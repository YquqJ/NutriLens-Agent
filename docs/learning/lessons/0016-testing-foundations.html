测试入门：自动检查“这次改动有没有弄坏原来的承诺”

目标：不要求你先学完 pytest。读完后，你应能看懂一条普通测试的输入、动作、预期，以及正确理解 passed / failed / skipped。

为什么要测试？

开发时，你在浏览器里手动点一次“记录午餐”，能看到它工作。但之后修改了 Supervisor、Service 或数据库模型，可能悄悄破坏“过敏未确认不能写库”这种旧行为。测试就是把这条承诺写成能反复运行的程序。

业务承诺：用户对海鲜过敏，未明确确认时，不能创建饮食记录。

自动检查：
给定“对海鲜过敏” + “虾” + “未确认”
调用创建记录
必须抛出指定异常，而且数据库仍然没有记录

它的价值不是替代思考，而是让每次改动后都能在几十秒内重新检查关键承诺，尽早发现回归。

一条测试的固定结构：AAA

步骤英文做什么
1Arrange准备输入和环境：用户、数据库、函数参数。
2Act执行被测代码：调用函数、接口或图。
3Assert比较实际结果和预期结果。
def test_mrr():
    # Arrange：排名和“正确答案”
    ranking = [5, 2, 9]
    relevant = {2, 9}

    # Act：运行项目函数
    actual = mrr(ranking, relevant)

    # Assert：第一个相关结果在第 2 位，所以 1 / 2
    assert actual == pytest.approx(0.5)

这来自 backend/tests/test_eval_metrics.py。5 无关，2 是第一个相关切片且排第 2，所以 MRR = 1/2。这里的 pytest.approx 是浮点数比较的容差写法，避免 0.1 + 0.2 这类二进制小数误差造成误报。

测试如何运行？

uv run pytest tests/test_eval_metrics.py -q
  1. pytest 会发现文件名/函数名以 test_ 开头的测试。
  2. 它逐条运行测试函数中的生产代码。
  3. 遇到 assert：条件为真，测试通过；条件为假，输出失败位置、实际值和预期值。
  4. 最后汇总，例如 13 passed。

结果到底说明什么？

结果真实含义不代表什么
passed代码满足了这一条测试给定的输入和预期。不代表整个系统没有任何 bug。
failed实际行为与测试预期不一致，需要定位是代码变了、规则变了，还是环境异常。不自动等于生产代码一定错。
skipped前提不具备，所以该测试没有执行。例如没有 API Key 的真实 LLM Eval。不等于通过。
最准确的说法是：“13 条测试通过”，而不是“项目已经绝对正确”。测试覆盖的是被写出来的场景；没写到的场景，测试不会替你发现。

怎样保证“预期”本身是对的？

  1. 预期来自明确规则：MRR 的公式、热量公式、权限规则、产品需求，而不是开发者随手猜的答案。
  2. 用独立方式校验：像 MRR 先手算；数据库测试直接查询落库结果；不要只 mock 自己刚写的同一段逻辑。
  3. 覆盖不同情形：正常输入、边界值、空值、异常输入、禁止副作用。例如“过敏未确认”和“过敏已确认”都要测。
  4. 失败时先理解差异：需求若真的变了，先更新规则和测试；需求未变，就修生产代码。不能为了让绿灯亮而删除断言。

对应到 Agent 项目

Agent 不确定的是模型怎样组织语言，不是所有事情都不确定。例如：user_id 必须来自运行时、hop_count 不得超过上限、HITL 前不得写库、恢复后不能重复写库，这些都可以像普通后端一样写测试。

模型答案的“好不好”才使用第 15 课的 Eval：题集、指标、人工抽样，而不是要求每次说出一模一样的话。

先做一个很小的自测

  1. 对 mrr([5, 2, 9], {2, 9}) 而言，Arrange、Act、Assert 分别是什么？
  2. 若测试显示 skipped，它和 passed 的区别是什么？
  3. “所有测试通过”为什么不能推出“系统绝对没有 bug”？
