Agent 测试与评估：怎样证明它可靠，也真的有用？

对应 backend/tests/ 与 app/rag/eval.py。目标：把“模型输出不稳定，所以没法测”的误解拆掉，并能在面试中说清测试与 Eval 的工程分工。

先记住一条边界

测试 Test评估 Eval
验证一个确定的契约是否满足。在一批样本上衡量质量趋势。
结果通常是 pass / fail。结果通常是一组分数、案例和回归差异。
适合 PR 门禁：快、稳定、无外部模型依赖。适合定期或手动运行：可能慢、有成本、会受模型版本影响。
例：确认前不得写饮食记录。例：RAG 的 Recall@8 是否比上次下降。
LLM 的自然语言答案不适合断言“必须等于这一整段字符串”；但围绕它的路由、工具调用、权限、写库、引用、拒答和数值事实，仍然有大量确定契约可以严格测试。

本项目的四层测试

  1. 纯函数单测：test_eval_metrics.py 对 recall_at_k、mrr、ndcg_at_k 传入固定排名，断言精确数字。MET、BMR 等公式也应属于这一层。
  2. Tool / Service 集成测试：test_allergy_guard.py 直接调用 Service，断言“有海鲜过敏且未确认”会抛 AllergyConfirmationRequired，并且数据库仍无记录。这是在保护副作用，不依赖模型是否听话。
  3. 图控制流测试：test_supervisor.py 用 RunnableLambda 伪造固定路由器，验证 goto、hop_count、重复派发拦截；test_supervisor_graph.py 用 MemorySaver 验证相同 thread_id 的历史能续上。
  4. 真实模型 / E2E / Eval：真实 embedding、pgvector、Postgres、LLM 的链路另跑。test_rag_eval.py 标注 pytest.mark.eval，没有 DASHSCOPE_API_KEY 时 skipif 跳过，避免把成本与不稳定性塞进每次快速回归。

桩（Stub）不是“假测试”

decision = RouteDecision(next_agent="diet_agent", task="记录午餐")
supervisor = make_supervisor_node(_stub_router(decision))
cmd = supervisor({"hop_count": 0, ...})

assert cmd.goto == "diet_agent"
assert cmd.update["hop_count"] == 1

此处的目标不是验证 qwen 会不会理解午餐，而是验证当路由决策已经给定时，图的代码是否正确地跳转和更新 State。两件事拆开测，失败时才知道该改 prompt、模型，还是改图代码。

HITL 最值得测的不是 UI 文案

第一次 invoke
→ 收到 __interrupt__
→ 数据库中尚无 DietRecord

相同 thread_id + Command(resume=确认数据)
→ 恢复执行
→ 恰好写入一条 DietRecord

test_interrupt_resume_through_graph 就在验证这条关键不变量。它还间接验证了 Checkpointer 能保存恢复所需的 pending work。生产级别还应补一条：同一个 resume 请求重放时，不会重复落两条记录，也就是幂等性。

RAG 指标：测“找到了没有”和“排得靠不靠前”

评测集 rag_queries.json 给每个问题写出应命中的 relevant_hashes。用内容 hash 而不用自增 id，是因为 seed 到另一套数据库后 id 会变化，内容 hash 更稳定。

指标它回答的问题例子
Recall@K前 K 条有没有找全相关资料？相关有 A、B；top-3 找到 A、B，Recall@3 = 1。
MRR第一个相关资料排第几？第一个相关结果在第 2 位，MRR = 1/2。
nDCG@K相关资料是否整体排得更靠前？同样命中 A、B，排在第 1、2 位比第 3、4 位分更高。
检索分数高，不等于回答一定可信。当前项目已测召回排序；下一步应增加回答层评估：每个结论能否被引用片段支持（faithfulness）、引用是否正确、库外问题是否恰当拒答（abstention）。

怎样断言 LLM 结果？

脆弱断言更好的契约断言
最终回答必须等于一整段指定文案最终回答包含必须出现的数值/实体；或符合 Pydantic schema
模型必须一字不差地解释过敏风险未确认时不写库；确认后恰好写一条；风险字段被返回
模型永远调用固定顺序的工具必须调用的工具被调用；禁止的副作用没有发生；总步数不超过上限
每次真实模型跑分都必须 100 分记录基线、模型/Prompt/索引版本，观察分数回归和失败案例

面试可说的改进方案

  1. 为 rag_queries.json 加版本和覆盖维度：同义改写、多跳问题、专业术语、库外问题、冲突资料。
  2. 保存每次 Eval 的模型版本、embedding 模型、chunk 策略、rerank 配置、数据集版本与指标，比较 delta；不能只留一份控制台输出。
  3. 在检索指标外，加答案级 faithfulness、citation correctness 和 abstention accuracy，并人工复核抽样案例。
  4. 给写操作补幂等键或已处理 resume 标记，测试重复 resume 不重复创建业务记录。

面试表达

“我把 Agent 的验证分成确定性测试和质量评估。路由 State 更新、权限、写库、HITL 前后副作用这些做无模型的快速门禁；模型、向量检索和数据库的真实链路用带 marker 的 E2E 与 golden dataset 评估。RAG 先看 Recall@K、MRR、nDCG，再补回答是否由证据支撑和库外拒答。这样模型可以变化，但系统的安全契约不会靠祈祷维持。”

自测

  1. 为什么不该断言 LLM 最终回答完全等于某一整段文字？
  2. 哪些测试应该作为快速 PR 门禁，哪些适合 pytest -m eval 单独运行？
  3. 若 Recall@8 上升，但 faithfulness 下降，可能发生了什么？
  4. 为 interrupt/resume 设计一条最重要的数据库不变量。
