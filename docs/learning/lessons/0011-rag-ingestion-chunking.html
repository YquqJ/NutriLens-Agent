RAG 离线链路：解析、切片、向量化、幂等导入

对应 rag/document_loader.py 与 db/seed_knowledge.py。目标：理解 RAG 的知识不是“上传文件就能查”，而是一套可重跑的数据管道。

完整导入流程

PDF / Markdown 原文件
  → extract_pdf_chunks
  → ExtractedChunk(content + page + section + chunk index + content hash)
  → embed_texts(chunk contents)
  → KnowledgeDocument（来源元数据）
  → KnowledgeChunk（正文 + 向量 + 引用定位）
  → query 时 retriever 使用它们

先分离两个职责

模块责任是否依赖外部服务
document_loader.py读取 PDF 文本、清洗、识别章节、切片否，可离线单测
embedding.py切片文本转固定维度向量是，Embedding API
seed_knowledge.py幂等更新文档和切片数据库记录是，数据库与 embedding

这叫 ingestion pipeline。把解析与入库拆开，失败更容易定位：是 PDF 无文本、切片策略问题、Embedding 超时，还是数据库写入失败。

章节感知切片

代码识别“第 X 章”“1.1 标题”“附录”，维护 current_chapter 和 current_section。每页形成 section block，再按长度切片。切片携带：page_number、section、全局 chunk_index。

章节前缀会被放回每个 chunk 正文。原因是一个 chunk 被单独召回时，仍应保留“这段内容在讲什么”的语境。

600 字符与 80 字符 overlap

_MAX_CHARS = 600 控制单段上限，防止 chunk 太长导致 embedding 语义混杂、塞给 LLM 时上下文浪费；_OVERLAP_CHARS = 80 只在单行超长时，让相邻窗口共享结尾/开头，避免一句话或关键条件刚好被截断。

注意：当前实现优先按原始行累积，不是对每个 chunk 都强制 overlap。这是“尊重段落边界优先”的轻量策略。

文件哈希与幂等更新

同一 source_key 已存在？
  ├─ 文件 SHA-256 相同且仍有 chunks → return 0，跳过
  └─ 文件哈希变化 / chunks 缺失
       → 删除该 document 的旧 chunks
       → 更新文档元数据
       → 新文本向量化
       → 写入新 chunks
       → commit

KnowledgeDocument 管“来源文件”，KnowledgeChunk 管“检索粒度”。文件变更时只重建这个文件的切片，不清空整个知识库。

两个 Hash 的用途不同

  • file_sha256(source PDF)：判断整份文件是否变更，决定是否需要重导。
  • ExtractedChunk.content_hash：标识某段正文内容，数据库唯一约束可避免同一文档重复插入相同切片。

真实运行结果与改进点

当前内置 PDF 共 13 页，解析得到 66 个切片。检查结果发现存在只有章节标题的极短 chunk；它向量信息密度低，可能占用候选名额。生产优化可设置最小正文长度，或将标题和下一段正文合并后再向量化。

切片质量决定 RAG 上限。chunk 太大：主题混杂、召回不准、上下文昂贵；太小：事实不完整、上下文丢失、候选过多。600/80 不是标准答案，应通过真实 query 的 Recall@K、回答忠实度和人工抽样调参。

失败边界

  • 文件不存在：抛 FileNotFoundError。
  • PDF 加密：拒绝导入。
  • 某页提取不到文本：拒绝静默入库，要求走未来 OCR 分支。
  • embedding 数量与 chunk 数不一致：抛异常，避免向量和正文错位。
  • 在 commit 前异常：当前 SQLAlchemy session 未提交，正常情况下不会留下半份新导入数据。

面试表达

“我把 RAG 知识导入实现为可重跑的离线管道：文档解析和切片保持确定性、可离线测试；每段携带页码和章节用于引用；文件哈希决定是否重建，文件变更时只删除对应文档的旧 chunk 后批量生成新 embedding。切片长度与 overlap 是可评估参数，不是写死的经验常量。”
