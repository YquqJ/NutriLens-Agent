Agent 前端：SSE 事件协议与可恢复状态机

对应 api/chat.py、views/ChatView.vue、components/HitlCard.vue。目标：理解一个 Agent 产品为什么不能只有“流式文本框”。

后端把图投影成 UI 事件

事件来自哪里前端作用
tokenLLM 文本分片追加 assistant 正文
agent_tracesupervisor update显示当前 worker
tool_callsAIMessage + ToolMessage 配对展示可审计的工具轨迹

done/error运行结束/异常收尾、落历史或展示错误

前端状态机

idle
  → streaming
  → interrupted (pendingMsg 指向同一条 assistant 消息)
  → resuming
  → done | error

busy = streaming || pendingMsg

busy 不只是按钮 loading。它禁止同一会话在确认未完成时再发送新消息，避免两个执行流同时操作同一条 LangGraph thread。

为什么不用“只流文本”

工具调用、证据、人工确认和最终回答有不同语义。把它们混进 token，会导致前端无法做确认卡片、无法可视化工具轨迹，也难以重放历史。因此后端使用 stream_mode=["messages", "updates"]，再转成稳定的业务 SSE 协议。

分片解析的前端基本功

网络 chunk 不等于一条 SSE 事件。streamRequest 用 buffer 累积文本，再以空行 \n\n 切帧，最后解析 event: 和 data:。这是流式接口最常见的边界问题。

确认后为何复用同一条消息

初次请求创建 live assistant 消息；收到 interrupt 后将它放到 pendingMsg。确认时继续把同一个 live 传给 streamRequest。因此 UI 从确认卡片自然过渡为最终回复，而不是凭空多一条 assistant 消息。

终稿为何覆盖 token

ReAct 流中的文本可能包含模型在工具间的过程话术。后端在 done 返回最终 state 的最后一条 AIMessage；前端用它覆盖 token 累积文本。用户看到的是结果，工具过程则去 Tool Trace 面板。

Agent 开发必须建立的安全边界

`Command(resume=...)` 是来自浏览器的输入，和普通 POST body 一样不可信。当前前端限制了克数范围，但后端恢复后的 confirmed["items"] 没有再次做完整 schema 校验，也把营养字段交给客户端传回。生产级实现应只接受“草稿条目 id + 修改后的 grams + acknowledgement”，在服务端按原始草稿重新计算营养、验证范围和过敏确认。

面试表达

“我把 LangGraph 的内部事件投影为一个前端可消费的 SSE 协议。前端以判别联合类型处理 token、路由、工具、引用和 interrupt；HITL 把同一条会话消息从 streaming 切到 pending，再经同一 thread_id resume。关键是把 resume 当作不可信边界，服务端必须重新验证和计算。”
