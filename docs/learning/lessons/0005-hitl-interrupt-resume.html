HITL：interrupt 暂停，resume 继续

对应 tools/diet.py:create_diet_record 与 api/chat.py:resume_chat。目标：理解确认卡片如何阻止写库、如何恢复，以及为什么恢复时前置代码必须可重复执行。

一次完整往返

LLM tool call
  → create_diet_record 生成 draft
  → assess allergy risks
  → interrupt(payload)
  → GraphInterrupt，整张图暂停并写 checkpoint
  → SSE 把 payload 发给前端
  → 用户确认/改克数/取消
  → Command(resume=value)，必须使用同一 thread_id
  → interrupt() 返回 value
  → 取消则返回 cancelled；否则最终校验并写库

payload 不是 AgentState

interrupt_payload 是给前端渲染确认卡片的数据：餐次、日期、食物草稿、过敏风险。它通过 __interrupt__ 暴露，不是通过 update 写入 State。checkpoint 仍会保存图当前的 State 与暂停位置。

为什么写库在 interrupt 之后

第一次执行到 interrupt() 会暂停；恢复时，LangGraph 可能从包含 interrupt 的节点重新执行。若写库放在 interrupt 前，第一次暂停前就可能已写入；恢复重跑又可能重复写入。因此 interrupt 前只能做可重复、无副作用的计算：组装草稿、查风险、构造 payload。

经验法则：任何可能被 resume 重放的代码，都不要直接发送邮件、扣款、写数据库。把副作用放在确认之后，并让 service 层继续做最终校验。

两种 resume

  • Command(resume={"items": items})：用户确认，也可以带修改后的克数。
  • Command(resume=False)：用户取消；工具立即返回 cancelled，不执行写库。

过敏确认是第二道闸

第一次确认后，如果有风险但没有 allergy_acknowledged=True，工具再次 interrupt()。用户删除风险食物后，代码还会重新评估最终条目。即使客户端绕过工具层，service 仍应拒绝未确认的风险写入。

面试表达

“HITL 不是让模型自己问一句确认，而是让图运行时真正暂停并持久化 checkpoint。前端提交后，以相同 thread_id 发送 Command(resume=...) 恢复；确认前不产生写库副作用，确认后再用最终用户编辑结果落库。”
