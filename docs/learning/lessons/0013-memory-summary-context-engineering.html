Memory：摘要压缩与上下文工程

对应 agents/memory.py、agents/graph.py、agents/supervisor.py。目标：理解长会话如何控制 Token、保留跨轮语义，又不把全部历史重复塞给每个 Agent。

先区分四样东西

概念内容用途
messages最近原始 Human/AI/Tool 消息短期上下文、ReAct 工具观察
summary早期对话的压缩要点跨轮指代消解、长期会话语义
checkpoint上述 state 与图执行进度跨请求恢复、HITL
UserProfile身高、目标、偏好、过敏等业务事实跨会话长期业务记忆

为什么需要摘要节点

messages 用 add_messages 一直追加。会话越长，Supervisor 和 Worker 每次要处理的 token 越多：成本、延迟和上下文窗口风险都会增长。摘要不是为了“保存更多”，而是为了把旧上下文压缩成更少 token。

在图中的位置

START → turn_reset → analyze_image → summarize → supervisor → worker

每条新的用户消息进入时，先恢复 checkpoint 中的旧 state，
再追加本轮 HumanMessage；若 messages 超阈值，才触发 summarize。

阈值逻辑

MAX_MESSAGES = 24
KEEP_TAIL = 8

len(messages) <= 24
  → return {}，不调用 LLM

len(messages) > 24
  → old = messages[:-8]
  → LLM 把 old（以及已有 summary）压缩为 new_summary
  → 用 RemoveMessage 删除 old
  → 只留最近 8 条原始消息

注意这里计数的是消息对象，不是用户轮数；一个 ReAct 工具调用会增加 AIMessage 和 ToolMessage，因此工具密集会话会更早触发压缩。

滚动摘要

第一次压缩：old messages → summary。后续压缩：existing summary + new old messages → updated summary。摘要提示词只保留身体数据、目标、偏好、已记录事项、进行中的计划、重要结论和待办，丢弃寒暄与过期临时信息。

这是“滚动摘要”，不是全文存档。全文用户可见历史仍在业务 messages 表；Agent 运行时的 messages 只保留近窗口。

为什么用 RemoveMessage

messages 的 reducer 是 add_messages，普通返回 {"messages": []} 不能清掉历史，只会追加。要删指定的旧消息，必须向 reducer 返回 RemoveMessage(id=...)。LangGraph 官方也将该原语用于摘要后删除被折叠历史。citeturn0search0

为什么 summary 只给 Supervisor

summary → Supervisor
messages + task → Worker

Supervisor 需要完整会话语义做路由和指代消解，例如把“昨天那顿再记一次”变成独立 task。Worker 收到明确 task 后，重点需要近期原始消息中的 ToolMessage，以完成本轮 ReAct；把摘要也塞给所有 Worker 会增加 token，且可能引入不相关历史干扰。

摘要的风险

  • 摘要模型可能漏掉关键偏好或错误合并事实，后续压缩还会放大该误差。
  • 摘要应保存“对话线索”，不能作为用户过敏、身份、余额等权威事实源。
  • 阈值按消息数而非 token 数，短消息与长消息被同等对待，成本控制不够精细。
  • 重要结构化事实应写入 UserProfile 或业务表，不能只依赖自然语言摘要。
生产改进：按 token 而非消息数触发；对 summary 做结构化 schema；为摘要版本、生成时间和来源消息范围留审计信息；对“过敏、权限、金额”等关键事实只信业务表。

测试证明什么

test_memory.py 注入假摘要器，验证未超阈值时不调用模型、超阈值时生成摘要并裁剪；再在真实 StateGraph 中验证 RemoveMessage 确实让 messages 只剩 8 条，最后验证 Supervisor 真的收到 summary。

面试表达

“Checkpointer 解决状态持久化，不解决上下文无限增长。我在图入口增加摘要节点：超过阈值时，将早期消息压缩为滚动 summary，并用 RemoveMessage 从 append-only messages 通道删除原文，只保留最近窗口。summary 仅注入 Supervisor 做跨轮指代消解；Worker 通过 task 获取消解后的目标，并保留近期工具观察。关键业务事实仍落 UserProfile 和业务表，不能把 LLM 摘要当作权威数据。”

自测

  1. 为什么 {"messages": []} 不能清空本项目的 messages？
  2. 为什么 summary 不应该作为过敏信息的唯一来源？
  3. 为什么工具调用频繁的会话会更早触发当前实现的摘要？
  4. 如果要让压缩更准确，为什么按 token 而不是按消息条数更合理？
