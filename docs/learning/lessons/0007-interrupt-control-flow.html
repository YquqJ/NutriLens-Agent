Interrupt 的真实控制流

对应 tools/diet.py:create_diet_record、api/chat.py:_run_graph_and_stream 和 resume_chat。目标：分清“流式输出”“图暂停”“新请求恢复”三件事。

第一次请求

POST /chat
  → StreamingResponse 开始消费 _run_graph_and_stream
  → for 迭代 graph.stream 产生的事件
  → search_food 的 token / updates 逐帧 yield
  → create_diet_record 调到 interrupt(payload)
  → LangGraph 保存 checkpoint，发出 __interrupt__
  → 后端 yield interrupt 事件与 done(interrupted=true)
  → 本次 HTTP 响应结束；没有 Python 调用栈继续等待

for 和 yield

for 逐个取图事件；yield 把当前转换后的 SSE 字符串交给 HTTP 响应，然后暂停生成器。客户端继续读取时，生成器从上次 yield 后面继续。它表示“增量产生”，不是“永不结束”。

第二次请求

POST /chat/resume
  → 使用同一 thread_id 读取 checkpoint
  → Command(resume=value)
  → 从保存的中断节点重新开始
  → create_diet_record 前置计算再次执行
  → 执行到同一个 interrupt(payload)
  → 这次 interrupt() 返回 value
  → 从 if confirmed is False 继续后面的代码
  → 最终 service 写库，ReAct 生成汇报，图结束
“从第 157 行继续”是理解结果，不是底层执行方式。准确说法是：节点从头重跑；重新遇到 interrupt 时，运行时把 resume 值作为该调用的返回值，因此 Python 逻辑随后自然走到第 157 行。

为什么不能保存 Python 调用栈

用户可能几分钟、几小时后才点击确认，期间服务进程可能重启、请求线程也早已释放。LangGraph 保存的是可序列化的状态、线程指针和中断信息，而不是某个 Python 函数的内存栈。checkpointer 因此是 HITL 和故障恢复的基础。

哪些代码会重跑

  • 中断所在节点之前的代码会重跑：本项目包括组装 draft、重新检查过敏风险、重新构造 payload。
  • 不会从整个外层图的 START 重新跑；恢复从 checkpoint 指向的中断节点开始。
  • 写库必须放在 interrupt 之后；否则重放可能造成重复副作用。

工程重点

  1. Durable execution：状态持久化后，长流程可跨请求继续。
  2. 事件协议：token、tool_calls、interrupt、done 分开，前端才能正确渲染。
  3. 幂等与重放：中断前代码应无副作用；生产写入还应考虑幂等键。
  4. 不可信恢复值：resume 来自浏览器，服务端要重新校验和计算。
  5. 异常边界：不要用裸 except Exception 包住 interrupt()，否则可能吞掉框架的中断信号。
