测试层级、Fixture 与“预期答案”

目标：看懂项目中为什么有的测试只调用一个函数，有的要创建用户和数据库，还有的要跑完整 Graph。

三种测试层级

层级检查什么依赖速度项目例子
Unit 单元测试一个函数/类的逻辑尽量无 DB、无 LLM最快test_eval_metrics.py 测 MRR
Integration 集成测试多个模块能否正确协作真实或测试数据库中等test_allergy_guard.py 测 Service + DB
E2E 端到端测试从入口到最终结果的完整链路Graph、Checkpoint、可能还有 LLM最慢test_interrupt_resume_through_graph

用前端类比：Unit 像只测一个 reducer；Integration 像测表单提交和 API 是否配合；E2E 像启动页面、输入文字、点击按钮，再检查数据库最终状态。

逐段拆一条项目测试

def test_service_blocks_agent_write_without_explicit_ack(allergy_user):
    db = SessionLocal()
    try:
        with pytest.raises(diet_service.AllergyConfirmationRequired):
            diet_service.create_diet_record(...)
        assert diet_service.get_diet_records(db, allergy_user, date.today()) == []
    finally:
        db.close()
  1. allergy_user 是 Fixture，提前创建一个带“对海鲜过敏”档案的测试用户。
  2. SessionLocal() 打开数据库会话。
  3. pytest.raises(...) 表示这里预期必须抛出指定异常；不抛或抛错异常，测试失败。
  4. 第二个 assert 检查副作用：异常发生后，数据库中仍然没有饮食记录。
  5. finally: db.close() 清理资源，避免一个测试污染后面的测试。
这条测试比“只检查返回错误文案”更可靠：它同时验证了安全规则和数据库没有被偷偷写入。

Fixture 是什么？

Fixture 就是测试专用的准备函数。它把重复的 Arrange 抽出来，让每条测试专注于自己的行为。测试函数声明参数名，pytest 就会自动调用同名 Fixture，并把结果注入进来。它很像前端测试里的 beforeEach，但可以有清晰的“准备 / 清理”。

Stub、Mock 与真实依赖

方式目的Supervisor 例子
真实依赖确认真实系统能联通真实 LLM、Postgres
Stub 桩返回预先指定的简单结果RunnableLambda(lambda _: decision)
Mock 模拟记录依赖是否被调用、参数是什么检查工具是否被调用一次

Supervisor 测试使用 Stub，是为了把“模型会不会正确路由”和“拿到路由结果后图代码是否正确”拆开。否则失败时不知道该查 Prompt 还是查 goto。

怎样判断测试的预期答案可靠？

  1. 有独立来源：公式来自定义，权限来自业务规则，数据库结果直接查询真实状态。
  2. 不要复制实现：如果测试和生产代码使用同一段计算逻辑，可能一起错；MRR 测试应先手算。
  3. 覆盖反例：不仅测“确认后能写”，还测“未确认不能写”；不仅测正常路由，还测 hop 上限。
  4. 故意制造错误：临时把生产代码中的 + 1 改成 + 2，测试应该失败。
  5. 避免过度 Mock：把所有函数都 Mock 掉，可能全绿，但真实模块根本没有连接。

测试金字塔

        E2E：少量，慢，验证完整链路
     Integration：适量，验证 DB / 模块协作
          Unit：大量，快，锁定纯逻辑

大多数规则应在 Unit 或 Integration 层快速捕获，少量关键链路再用 E2E 验收。真实 LLM 更像单独的质量评估，不应成为每次改一行代码都必须等待的唯一防线。

自测

  1. 为什么过敏测试不仅要断言异常，还要查询数据库为空？
  2. allergy_user Fixture 主要替你解决了什么问题？
  3. 若把 Supervisor 的 LLM 换成 Stub，测试还剩下什么价值？
  4. 怎样故意改一处生产代码，验证某条测试真的能抓 bug？
