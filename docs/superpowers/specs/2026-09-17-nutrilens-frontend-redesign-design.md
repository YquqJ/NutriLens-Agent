# NutriLens 前端改版设计规格

## 目标

在既有 Vue 3 前端中重建 NutriLens 的日常健康管理体验：以 `#16a34a` 为主色的明亮薄荷绿系统，统一今日看板、月历记录、Agent 对话、计划入口和身体档案。保持现有认证、饮食/运动记录、SSE 对话、HITL 饮食确认、引用和看板接口可用。

本阶段仅实施前端。后端尚无可持久化计划的领域模型和 API，因此计划页必须明确呈现“通过对话生成计划”的入口与接口待接入状态，不能把原型中的静态计划内容伪装成用户真实数据。

## 已确认的产品决策

- 主主题色固定为 `#16a34a`；页面以白色/近白背景和浅薄荷绿选中态为主，不使用大面积深绿侧栏或深色内容卡。
- 首页为“今日健康操作台”，主信息顺序为：今日能量状态、快捷记录、7 日趋势、AI 洞察。
- 记录页面以月历为主视图：红点代表当日热量超标，绿色点代表目标内，灰点代表无记录；“食”和“动”标记分别表示当天存在饮食/运动记录。
- 对话继续作为 Agent 的主入口，保持会话、流式生成、工具轨迹、饮食 HITL 确认卡和 RAG 引用抽屉。
- 计划由对话生成和调整；完整的计划模块在后端落地前以“开始生成计划”入口和可解释空状态承接，不能从聊天富文本中解析并伪造结构化计划。
- 身体档案继续使用真实 profile API；BMR、TDEE、热量目标作为只读测算结果展示。

## 信息架构

`AppShell` 提供五个一级入口：

1. 今日 `/dashboard`
2. 记录 `/records`
3. 智能对话 `/chat`
4. 饮食计划 `/plan`
5. 身体档案 `/profile`

桌面端使用浅色左侧导航；窄屏退化为顶部/底部紧凑导航。所有视图使用同一页面标题区、卡片边框、状态色和数字字体规则。

## 页面行为

### 今日

- 读取既有 dashboard summary 和 7 日 trend API。
- 显示摄入、运动消耗、目标、剩余额度和宏量营养素。
- 将当天是否超标、是否有饮食记录、是否有运动记录作为记录月历的数据来源。
- 快捷按钮导航至对话或记录，不新增不存在的后端写入路径。

### 记录

- 支持月份选择和日期选择；当前接口仅按日期读取 records，前端按可见月逐日请求/汇总并管理加载与错误状态。
- 每个日期格展示状态点、饮食/运动标记和简化热量信息。
- 选中日期使用既有饮食/运动列表和汇总结果作为详情来源。
- 编辑、删除、手动添加能力沿用当前页面的真实 API。

### 智能对话

- 不改变 SSE 协议、会话 API 或当前饮食确认流程。
- 视觉上将会话列表、对话主区和健康上下文分区；窄屏隐藏次要上下文。
- 计划入口带预填提示文案，但仅发送正常聊天消息；不会尝试持久化计划。

### 饮食计划

- 本期不创建 mock 计划数据。
- 空状态说明计划将基于档案、偏好和记录由 Agent 生成；主操作导航至对话，并将“帮我生成饮食和运动计划”预填到输入框。
- 为未来计划 API 预留 `PlanView`、计划类型和 API module 的独立边界。

### 身体档案

- 保持原有可编辑表单和 profile API。
- 使用更清晰的分区和薄荷绿色能量测算面板展示真实 BMR/TDEE/目标摄入数据。

## 组件与数据边界

- `AppShell.vue`：布局、导航、当前路由状态；不承载业务请求。
- `DashboardView.vue`：只消费 summary/trend。
- `RecordsView.vue`：消费 diet/exercise records 和 daily summary，负责月历派生状态。
- `ChatView.vue`：保持聊天状态机；接收 query 参数预填消息。
- `PlanView.vue`：不读取聊天历史、不解析模型文本；仅提供到 ChatView 的计划生成入口。
- `ProfileView.vue`：消费 profile API。
- 新增 `calendar.ts`：纯函数负责月历日期、状态和标记派生，使用 Vitest 单测。

卡片采用 8px 左右圆角、细边框和极轻阴影；颜色不会单独承担信息表达，月历同时保留文字图例和饮食/运动标记。图标使用现有 Element Plus 图标库。

## 非目标

- 不在本期新建 `plans`、`plan_items` 或 `plan_item_completions` 后端表。
- 不调整 Supervisor 星型拓扑，不新增运动计划 Agent。
- 不修改已有饮食、运动、档案、聊天 API 契约。
- 不使用静态伪数据暗示真实计划已被保存。

## 后续计划后端接口边界

当计划持久化进入后端时，`plan_agent` 通过结构化草案和确认中断保存 `Plan` 与 `PlanItem(kind = meal | exercise)`；计划页从计划 API 读取已确认版本，实际记录只做完成度对照，不改写计划。这是独立后端子项目，不阻塞本次前端改版。

## 验收标准

- `npm run type-check` 与 `npm run build` 通过。
- 五个一级路由可访问，导航状态正确。
- 现有登录、看板、记录管理、聊天流式、饮食确认和档案编辑不回归。
- 月历日期状态可由真实 records/summary 派生，包含超标、目标内、无记录、饮食与运动标记。
- 375px 和桌面宽度下文本不溢出，导航与核心操作可见。
